ARCHITECTURE DRIVERS
Các architecture drivers chính được rút ra từ SRS gồm:
| Driver | Architecture Implication |
|---|---|
| Modular Monolith | Một Spring Boot deployable nhưng chia business module rõ |
| Backend authoritative | Business validation và state transition nằm ở Backend |
| Inventory concurrency | Reservation phải chống overselling |
| Checkout idempotency | Duplicate request không tạo duplicate Order |
| payOS webhook duplication | Payment processing phải idempotent |
| External payOS call | Cần compensation vì không có distributed transaction |
| Historical Order data | OrderItem lưu immutable snapshot |
| VND monetary rule | Một pricing calculation boundary dùng chung |
| Multi-ADMIN | Notification read-state phải per recipient |
| Google Login + JWT | Identity boundary riêng |
| Runtime DB authority | JWT role claim không đủ để authorize |
| S3 image storage | Binary nằm ngoài PostgreSQL |
| Reporting | Read-only capability, không own business transaction data |
| AWS deployment | Runtime phải deploy được trên AWS với PostgreSQL và S3 |
| Team nhỏ | Tránh microservices và operational overhead không cần thiết |
SRS xác định `Payment.status` là authoritative, một Order có đúng một Payment, payment success commit Inventory nhưng Order vẫn `NEW`, và unsuccessful terminal payment phải cancel Order/release reservation.

5.2. Architecture Assumptions
Các nội dung sau là Architecture Assumption, không phải business requirement mới:
AA-001 – Single Spring Boot Runtime
Backend business modules được đóng gói và deploy dưới dạng một Spring Boot runtime/deployable.
AA-002 – Shared PostgreSQL Instance
Các module cùng sử dụng một PostgreSQL database instance nhưng mỗi module sở hữu logical tables/data của mình.
Shared database không đồng nghĩa mọi module được phép trực tiếp modify table của module khác.
AA-003 – In-process Module Communication
Module communication chủ yếu sử dụng:
```text
Application Service Interface
Read-only Query Interface
Internal Application Event
Application Orchestrator
```
Không cần distributed message broker.
AA-004 – Commerce Application Coordination Layer
Một application-level Commerce Application Coordination Layer chịu trách nhiệm điều phối các cross-module business flow phức tạp.
Layer này không sở hữu authoritative business data và không phải actor/business feature mới.
Các logical orchestrator/use case responsibility bên trong layer gồm:
```text
Checkout Orchestrator
Payment Result Orchestrator
Order Cancellation Orchestrator
Manual Refund Recording Orchestrator
```
Đây là logical responsibility, không phải bốn architecture module độc lập và không bắt buộc ánh xạ một-một thành Java class.
Exact class/package structure thuộc `04_IMPLEMENTATION_SPEC`.
AA-005 – Persistent Notification First
Notification persistence là authoritative notification state.
SSE, nếu triển khai, chỉ là delivery enhancement.
ARCHITECTURE PRINCIPLES
AP-001 – Business Capability First
Backend không tổ chức toàn bộ codebase theo global packages:
```text
controller/
service/
repository/
```
Thay vào đó:
```text
identity/
catalog/
cart/
inventory/
order/
payment/
notification/
reporting/
```
Mỗi module có internal layers riêng.
AP-002 – Single Data Owner
Mỗi business entity có đúng một owning module.
Module khác chỉ:
```text
query
request operation
consume event
```
Không trực tiếp thay đổi authoritative state thuộc module khác.
AP-003 – Backend Authority
Browser và Frontend không authoritative đối với:
```text
role
authorization
price
discount effectiveness
rounding
inventory
order state
payment state
refund eligibility
business time
```
---
AP-004 – Explicit Cross-module Interaction
Cross-module call phải thông qua module public application interface hoặc event.
Không gọi trực tiếp repository/entity nội bộ của module khác.
AP-005 – Avoid Cyclic Dependencies
Runtime business flow có thể liên quan nhiều module hai chiều về mặt nghiệp vụ, nhưng compile-time dependency phải được kiểm soát thông qua Commerce Application Coordination Layer, ports hoặc internal event.
AP-006 – Transactional Core, Compensated External Integration
PostgreSQL operation có thể dùng local transaction.
Các external systems:
```text
Google
payOS
Amazon S3
```
không tham gia PostgreSQL ACID transaction.
Do đó external integration cần:
```text
idempotency
retry khi appropriate
compensation
observability
```

ARCHITECTURE STYLE
MODULAR MONOLITH
8.1. Definition
System được deploy như:
```text
1 Spring Boot Backend Application
```
nhưng bên trong chia thành các module business độc lập về logical ownership.
Không áp dụng microservice boundary.
8.2. Benefits for Current Scope
Modular Monolith phù hợp vì:
business domain chưa cần independent deployment;
team nhỏ;
checkout yêu cầu transaction consistency mạnh;
Order/Payment/Inventory có nhiều invariant liên kết;
giảm distributed-system complexity;
vẫn cho phép module ownership rõ;
dễ chia ownership cho team;
dễ refactor thành service riêng trong tương lai nếu thực sự cần.
8.3. Module Encapsulation Rule
Mỗi module chỉ expose:
```text
Application Commands
Application Queries
Published Internal Events
Data Transfer Contracts cần thiết giữa module
```
Các thành phần internal như entity/repository không được xem là public dependency.

13.7. NOTIFICATION MODULE
Purpose
Lưu và cung cấp Notification cho nhiều ADMIN.
Owned Data
```text
Notification
NotificationRecipient
```
Architecture Decision ADR-016
Chọn logical model:
```text
Notification
+
NotificationRecipient
```
thay vì duplicate toàn bộ Notification cho từng ADMIN.
Rationale
Ưu điểm:
```text
business event chỉ lưu một lần
message/reference nhất quán
read state tách riêng từng recipient
giảm duplicate business data
```


CRITICAL BUSINESS FLOWS
30.1. CANONICAL CHECKOUT SEQUENCE
```mermaid
sequenceDiagram
    actor U as USER
    participant FE as Next.js
    participant C as Commerce Coordination
    participant Cart as Cart
    participant Cat as Catalog Pricing
    participant Inv as Inventory
    participant Ord as Order
    participant Pay as Payment
    participant Ext as payOS
    participant Noti as Notification

    U->>FE: Checkout
    FE->>C: Checkout request

    C->>Cart: Load and validate Cart
    Cart-->>C: Cart items

    C->>Cat: Validate Product and evaluate Discount
    Cat->>Cat: Apply BR-TIME-001
    Cat->>Cat: Apply BR-MONEY-001
    Cat-->>C: Authoritative rounded sellingPrice

    C->>C: Calculate Order total

    C->>Inv: Validate availability
    Inv-->>C: Availability valid

    C->>Ord: Create Order
    C->>Ord: Create OrderItems
    Ord-->>C: Order NEW

    C->>Inv: Reserve Inventory
    Inv->>Inv: Record InventoryTransaction.RESERVE
    Inv-->>C: RESERVED + RESERVE audit

    C->>Pay: Create Payment PENDING
    Pay-->>C: Local Payment

    C->>Pay: Create payOS payment information
    Pay->>Ext: Create payment
    Ext-->>Pay: Payment information
    Pay->>Pay: Persist external correlation when available
    Pay-->>C: External payment information created

    C->>Cart: Remove checked-out items
    C->>Noti: Persist NEW_ORDER

    C-->>FE: Payment information
    FE-->>U: Show QR or payment link
```
Architecture Explanation
Canonical checkout phải giữ đúng mutation order authoritative từ SRS:
```text
USER Checkout
↓
Load Cart
↓
Validate Cart Items
↓
Validate Product
↓
Recalculate authoritative sellingPrice
↓
Apply BR-TIME-001
↓
Apply BR-MONEY-001
↓
Calculate Order total
↓
Validate Inventory availability
↓
Create Order
↓
Create OrderItems
↓
Reserve Inventory
↓
Create InventoryTransaction.RESERVE
↓
Create Payment PENDING
↓
Call payOS Create Payment Information
↓
payOS creation succeeds
↓
Persist external payment correlation data when available
↓
Remove checked-out CartItems
↓
Create NEW_ORDER Notification
↓
Return payment information
```
`Availability Validation` không phải `Inventory Reservation Mutation`.
Inventory availability có thể được validate trước Order creation, nhưng mutation `Reserve Inventory` phải xảy ra sau `Create Order` và `Create OrderItems`.
Successful checkout initiation kết thúc với:
```text
Order = NEW
Payment = PENDING
Inventory = RESERVED
checked-out CartItems = removed
NEW_ORDER = persisted
```
Pricing được recalculate và rounded ở Backend. Payment chưa `PAID` tại giai đoạn này.
Tất cả logical orchestrator trong sequence thuộc cùng `Commerce Application Coordination Layer` và không sở hữu business state.
External payOS creation success không tự động đồng nghĩa toàn bộ checkout initiation đã được local-finalized. Successful checkout initiation response chỉ được trả sau khi required Phase C finalization outcome đã hoàn tất.
Nếu Phase C bị gián đoạn sau khi payOS creation đã thành công, operation phải đi vào `CG-007 – Successful Checkout Finalization` recoverable finalization path.
Recovery capability không cho phép Backend coi checkout là successfully finalized trước khi required Phase C outcome thực sự hoàn tất.
30.2. CHECKOUT CONSISTENCY BOUNDARY
PostgreSQL transaction không thể bao trùm payOS external system.
Architecture chia flow thành logical phases nhưng không khóa exact Spring transaction boundary.
Phase A – Local Preparation
```text
Create Order
Create OrderItems
Reserve Inventory
Create InventoryTransaction.RESERVE
Create Payment PENDING
```
Các state này phải đạt một consistent business outcome theo `CG-001`.
Phase B – External Payment Creation
```text
Call payOS Create Payment Information
```
External payOS operation không thuộc PostgreSQL ACID transaction.
Phase C – Successful Checkout Finalization
```text
Persist external correlation data when available
Clear checked-out CartItems
Persist NEW_ORDER Notification
Return payment information
```
Phase C phải tuân theo `CG-007 – Successful Checkout Finalization`.
Return payment information chỉ xảy ra sau khi các required local finalization action trước đó đã hoàn tất thành công.
Nếu Phase B đã SUCCESS nhưng Phase C local finalization chưa hoàn tất, Backend không được return successful checkout initiation result. Operation phải đi vào `CG-007` recoverable finalization path.
Trường hợp này không được classify như Phase B/payOS creation failure, không được xử lý như `CG-005`, và không được coi recovery capability là sự thay thế cho Phase C completion.
Failure Compensation
Nếu Phase B thất bại cuối cùng:
```text
Payment = FAILED
Order = CANCELLED
Inventory = RELEASED
InventoryTransaction.RELEASE recorded
Cart retained
No NEW_ORDER
```
Operation phải idempotent, consistent và observable.
Vì `Payment = FAILED` là terminal unsuccessful state, persistent `PAYMENT_FAILED` handling tuân theo `CG-003` và SRS Notification semantics; điều này không làm `NEW_ORDER` được tạo.
Exact local transaction split, compensation transaction, retry và `@Transactional` placement thuộc `04_IMPLEMENTATION_SPEC`.
30.3. PAYOS CREATION FAILURE SEQUENCE
```mermaid
sequenceDiagram
    participant C as Commerce Coordination
    participant Ord as Order
    participant Inv as Inventory
    participant Pay as Payment
    participant Ext as payOS
    participant Cart as Cart
    participant Noti as Notification

    C->>Ord: Order already NEW with OrderItems
    C->>Inv: Inventory already RESERVED
    C->>Pay: Payment already PENDING

    Pay->>Ext: Create payment information

    Pay-->>C: External creation failed

    C->>Pay: Transition FAILED
    C->>Ord: Transition CANCELLED
    C->>Inv: RELEASE reservation exactly once
    Inv->>Inv: Record RELEASE transaction
    C->>Cart: Keep CartItems
    C->>Noti: Persist PAYMENT_FAILED with FAILED status
```
Architecture Explanation
`NEW_ORDER` không được tạo trong flow này.
Compensation outcome:
```text
Payment = FAILED
Order = CANCELLED
Inventory = RELEASED
InventoryTransaction.RELEASE recorded
Cart retained
No NEW_ORDER
```
Operation phải idempotent, consistent và observable để retry compensation không release stock nhiều lần.
`PAYMENT_FAILED` persistence phản ánh actual terminal status `FAILED` theo SRS Notification semantics.
30.4. PAYMENT SUCCESS WEBHOOK SEQUENCE
```mermaid
sequenceDiagram
    participant Ext as payOS
    participant API as Webhook Boundary
    participant Pay as Payment
    participant Coord as Commerce Coordination
    participant Inv as Inventory
    participant Ord as Order
    participant Noti as Notification

    Ext->>API: Webhook
    API->>Pay: Verify authenticity and locate Payment

    Pay->>Pay: Idempotency check

    alt Already processed
        Pay-->>API: No duplicate business effect
    else Valid new success
        Pay->>Pay: Transition to PAID
        Pay-->>Coord: Payment success result
        Coord->>Inv: Commit reserved Inventory
        Inv->>Inv: Record SALE transaction
        Coord->>Ord: Keep Order NEW
        Coord->>Noti: Create PAYMENT_SUCCESS
        Coord-->>API: Processing complete
    end
```
Architecture Explanation
Client browser redirect không có authority để mark Payment `PAID`.
Chỉ verified payOS webhook/event có thể kích hoạt payment-success transition.
Order vẫn `NEW` sau payment success. SRS xác định `Payment → PAID`, Inventory commit exactly once và Order remains `NEW`.

CG-006 – Manual Refund Recording


```text

```
Không có Inventory mutation và không restore Inventory lần hai.
CG-007 – Successful Checkout Finalization
`CG-007` áp dụng khi `CG-001` đã hoàn tất và payOS Create Payment Information đã CONFIRMED SUCCESS, nhưng một hoặc nhiều local operation thuộc Phase C chưa hoàn tất.
Precondition:
```text
Order = NEW
OrderItems created
Inventory = RESERVED
InventoryTransaction.RESERVE recorded
Payment = PENDING
payOS Payment Information creation = CONFIRMED SUCCESS
```
External payment correlation data có thể đã được persist hoặc đang chờ hoàn tất trong local finalization.
Required final outcome:
```text
external payment correlation persisted when available
+
checked-out CartItems removed
+
NEW_ORDER persisted
+
Order remains NEW
+
Payment remains PENDING
+
Inventory remains RESERVED
```
Backend chỉ được return successful checkout initiation result sau khi toàn bộ required Phase C finalization outcome đã hoàn tất thành công.
`Recoverability ≠ Successful Finalization`.
Nếu payOS Create Payment Information đã thành công nhưng một local operation sau đó thất bại, ví dụ:
```text
persist external correlation fails
or
clear checked-out CartItems fails
or
persist NEW_ORDER fails
```
thì đây không phải `CG-005 – payOS Creation Failure Compensation` và Backend không được return successful checkout initiation result. Architecture phải đưa operation vào `CG-007` recoverable finalization path để retry/resume.
Nếu Phase C bị gián đoạn sau payOS creation success, hệ thống phải giữ đủ correlation/recovery information để operation có thể được retry/resume idempotently. Recovery capability không làm thay đổi canonical order và không cho phép mô hình normal flow kiểu `Return Success → recover Cart later → create NEW_ORDER later`.
Retry/resume/recovery phải có idempotent logical effect để bảo đảm:
```text
one logical checkout
→ one Order
→ one Payment
→ one Inventory reservation
→ one logical Cart clearing effect
→ one logical NEW_ORDER business notification
```
Retry/resume không được:
```text
create duplicate Order
create duplicate OrderItems
create duplicate Payment
create second payOS Payment Information without explicit allowed correlation behavior
reserve Inventory twice
create duplicate InventoryTransaction.RESERVE
remove unrelated CartItems
create uncontrolled duplicate NEW_ORDER
```
Cart finalization chỉ được remove các `checked-out CartItems` thuộc logical checkout operation; không được blindly clear toàn bộ Cart. Retry Cart finalization phải giữ idempotent logical effect.
`NEW_ORDER` vẫn đại diện successful checkout initiation. Retry Phase C phải dùng logical business-event deduplication để không tạo uncontrolled duplicate Notification. Exact deduplication key/schema thuộc `04_IMPLEMENTATION_SPEC`.
Trong `CG-007`:
```text
Payment remains PENDING
Inventory remains RESERVED
Order remains NEW
```
payOS Payment Information creation success không có authority để chuyển Payment sang `PAID`, và Inventory không được `COMMIT SALE` cho tới verified payment success webhook/event. Retryable local finalization error sau external success không tự tạo business cancellation rule mới và không tự release Inventory trái với frozen business semantics.
`03_SYSTEM_ARCHITECTURE` chỉ định required consistent/recoverable business outcome. Exact `@Transactional` placement, retry library/count/backoff, recovery/outbox/workflow storage, idempotency key format, database schema, Java class và scheduler thuộc `04_IMPLEMENTATION_SPEC`.
CONCURRENCY ARCHITECTURE
32.1. Critical Race Conditions
| Race Condition | Risk | Required Architecture Outcome |
|---|---|---|
| Concurrent checkout same Product | Oversell | Only valid stock reservation succeeds |
| Duplicate checkout | Duplicate Order | Same logical operation produces one Order |
| Duplicate webhook | Double stock commit | One Payment business transition |
| Concurrent expiration/webhook | Release and commit race | One valid terminal outcome |
| Concurrent Inventory adjustment | Invalid quantity | Inventory invariants maintained |
| Concurrent ADMIN demote/block | Zero ADMIN | At least one ACTIVE ADMIN remains |
| Duplicate cancellation | Double restore/release | Exactly-once business effect |
| Duplicate manual refund request | Invalid repeated refund status | Single valid transition |

ARCHITECTURE DECISIONS
ADR-001 – Modular Monolith
Context
Business capability liên quan chặt chẽ và team nhỏ.
Decision
Một Spring Boot runtime với business module boundaries.
Rationale
Giảm distributed-system complexity nhưng giữ maintainability.
Consequences
Modules phải enforce internal visibility và ownership.
Related SRS
```text
Architecture Constraint
NFR-MAINT-*
```
---
ADR-002 – PostgreSQL as Transactional Source of Truth
Context
Order, Payment, Inventory và User yêu cầu strong transactional consistency.
Decision
PostgreSQL giữ authoritative relational business state.
Rationale
Phù hợp SRS và transaction model của Modular Monolith.
Consequences
Cross-module data access phải respect ownership.
ADR-003 – Backend Authoritative Business Rules
Context
Frontend không phải security/business trust boundary.
Decision
Backend tính giá, validate state, authorize role/status và quyết định expiration.
Rationale
Ngăn client manipulation và giữ business rule nhất quán.
Consequences
Frontend chỉ hỗ trợ UX và render authoritative response.
ADR-004 – payOS Isolated Behind Payment Boundary
Context
payOS là external system và là payment gateway duy nhất.
Decision
Chỉ Payment module/integration adapter biết payOS protocol.
Rationale
Giảm coupling và không làm Order/Inventory phụ thuộc external payment protocol.
Consequences
Order/Inventory/Cart không import payOS-specific types hoặc protocol knowledge.
ADR-005 – Amazon S3 for Product Image Binary
Context
SRS freeze Amazon S3 cho Product Image binary.
Decision
Binary nằm S3, PostgreSQL lưu metadata/reference.
Rationale
Tách object binary khỏi relational transactional data và tuân thủ SRS.
Consequences
Architecture phải handle DB/S3 partial failure bằng consistency, compensation/retry khi phù hợp và observability.
ADR-006 – Inventory Reservation Model
Context
Checkout cần chống oversell trước Payment success.
Decision
Dùng logical model:
```text
quantity
reservedQuantity
availableQuantity
```
Rationale
Reservation tách stock đang chờ Payment khỏi physical quantity đã commit.
Consequences
Reservation phải reserve/release/commit exactly once về business effect và giữ Inventory invariants.
ADR-007 – One Order One Payment
Context
SRS freeze cardinality một Order có đúng một Payment.
Decision
Một Order chỉ có một Payment; failed/cancelled/expired Order không reuse cho Payment attempt mới.
Rationale
Giữ payment lifecycle đơn nghĩa và phù hợp frozen SRS.
Consequences
User muốn mua lại phải thực hiện checkout mới → Order mới → Payment mới.
ADR-008 – Per-recipient Notification Read State
Context
Nhiều ADMIN đọc cùng Notification độc lập.
Decision
Logical model:
```text
Notification
1
→ many
NotificationRecipient
```
Rationale
Một business Notification có thể dùng chung nội dung nhưng read-state phải độc lập theo ADMIN recipient.
Consequences
Notification query cần recipient relationship; không dùng global ADMIN `isRead`.
ADR-009 – Business Time Handling
Context
Discount, reporting, expiration và business-facing time cần cùng semantics.
Decision
Business timezone:
```text
Asia/Ho_Chi_Minh
UTC+07:00
```
Backend authoritative.
Rationale
Tránh khác biệt interpretation giữa Frontend, Backend và reporting/business rules.
Consequences
Persistence representation phải normalize consistently; exact representation thuộc `04_IMPLEMENTATION_SPEC`.
ADR-010 – VND Monetary Calculation Boundary
Context
PERCENTAGE Discount có thể tạo fractional VND.
Decision
Pricing boundary áp dụng:
```text
rawSellingPrice
→ HALF_UP nearest 1 VND
→ sellingPrice
```
trước line-total calculation.
Rationale
Giữ authoritative monetary values là integer VND và đồng nhất từ Product tới Payment.
Consequences
Frontend không recalculate authoritative values; `Payment.amount = Order.totalAmount` phải được bảo toàn.
ADR-011 – Commerce Application Coordination Layer for Cross-module Flows
Context
Checkout, payment result, cancellation và manual refund liên quan nhiều data owner.
Decision
Commerce Application Coordination Layer orchestrates public module interfaces và business consistency groups.
Rationale
Tránh circular module dependency trong khi vẫn điều phối cross-module consistency.
Consequences
Commerce Application Coordination Layer không own authoritative business data/domain state và không direct access foreign repositories.
ADR-012 – No External Message Broker
Context
Current SRS không yêu cầu Kafka/RabbitMQ và scope/team chưa cần distributed messaging infrastructure.
Decision
Use synchronous orchestration và optional in-process application events; không yêu cầu external message broker.
Rationale
Giảm operational/distributed complexity cho Modular Monolith hiện tại.
Consequences
Business-critical persistence không phụ thuộc best-effort asynchronous delivery; future external broker cần architecture revision.
ADR-013 – Persistent Notifications Before Real-time Delivery
Context
Persistent Notification là required capability; SSE chỉ SHOULD.
Decision
Persist Notification trước; realtime delivery là secondary enhancement.
Rationale
Không để realtime connection availability quyết định durability của business Notification.
Consequences
Notification remains queryable after SSE failure và SSE failure không rollback core business operation.
ADR-014 – Next.js Server/Client Data Fetching Boundary
Context
Next.js hỗ trợ cả server-side và client-side data fetching, trong khi từng page/use case có yêu cầu interaction, SEO và freshness khác nhau.
Decision
Next.js có thể sử dụng Server-side hoặc Client-side data fetching tùy use case. Backend API vẫn là authoritative source.
Rationale
Giữ flexibility của Next.js mà không chuyển business authority sang Frontend.
Consequences
Exact caching, rendering, revalidation và page-level fetching strategy thuộc `04_IMPLEMENTATION_SPEC`.
ADR-015 – Shared PostgreSQL with Logical Module Ownership
Context
Modular Monolith sử dụng một PostgreSQL database instance nhưng các module cần ownership rõ để tránh coupling và foreign mutation.
Decision
```text
One PostgreSQL database instance
+
logical module ownership
+
no direct foreign repository mutation
```
Rationale
Giữ transactional simplicity của Modular Monolith mà vẫn bảo vệ module boundaries.
Consequences
Không tạo database-per-module; cross-module read/mutation phải đi qua public module interfaces hoặc Commerce Application Coordination Layer.
ADR-016 – Notification + NotificationRecipient Model
Context
Notification được gửi tới nhiều ADMIN nhưng read-state cần độc lập theo từng recipient.
Decision
```text
Notification
1
→ many
NotificationRecipient
```
Read state thuộc từng ADMIN recipient.
Rationale
Tránh duplicate toàn bộ business Notification trong khi vẫn giữ independent read state.
Consequences
Notification persistence/query phải hỗ trợ recipient relationship; không có one global ADMIN `isRead`.
ADR-017 – Static Content Is Frontend-owned
Context
SRS chỉ yêu cầu static `FAQ`, `Policy`, `Contact` và không có Backend Admin CRUD/CMS.
Decision
```text
FAQ
Policy
Contact
→ Next.js static/config
```
Không có Spring Boot Content Module, Content DB table, CMS hoặc Admin Content CRUD.
Rationale
Phù hợp frozen scope và loại bỏ transactional/backend ownership không cần thiết.
Consequences
`FR-CONTENT-*` map tới Next.js Static Content Capability; static content không tham gia PostgreSQL transactional ownership.

FINAL ARCHITECTURE INVARIANTS
```text
1. Hệ thống là Modular Monolith.

2. Backend Spring Boot là authoritative business boundary.

3. PostgreSQL là transactional source of truth.

4. Frontend không quyết định authoritative authorization, Product price,
   Discount effectiveness, Order total, Payment status, Inventory state,
   Refund eligibility hoặc business time.

5. Product không có Variant.

6. Product không có Size.

7. Product không có Color.

8. Order Status chỉ gồm:
   NEW,
   CONFIRMED,
   COMPLETED,
   CANCELLED.

9. Không tồn tại SHIPPING Order Status.

10. Một Order có đúng một Payment.

11. payOS là payment gateway duy nhất.

12. Payment.status là authoritative Payment state.

13. Payment success không auto-confirm Order.

14. Payment success giữ:
    Order = NEW,
    Payment = PAID,
    Inventory = COMMITTED.

15. NEW → CONFIRMED chỉ hợp lệ khi Payment = PAID.

16. CONFIRMED → COMPLETED chỉ hợp lệ khi Payment = PAID.

17. USER không được tự cancel Order.

18. ADMIN chỉ cancel NEW hoặc CONFIRMED theo SRS state rules.

19. Inventory reservation phải concurrency-safe.

20. availableQuantity = quantity - reservedQuantity.

21. RESERVE chỉ tăng reservedQuantity.

22. RELEASE chỉ giảm reservedQuantity.

23. SALE giảm quantity và reservedQuantity.

24. CANCEL_ORDER restore tăng quantity và không thay đổi reservedQuantity.

25. Inventory commit/release/restore phải exactly-once về business effect.

26. Checkout phải chống duplicate Order.

27. payOS Webhook phải được verify.

28. payOS Webhook processing phải idempotent.

29. Duplicate webhook không được commit Inventory hai lần.

30. Duplicate webhook không được tạo duplicate Payment transition.

31. Payment FAILED/CANCELLED/EXPIRED phải dẫn tới:
    Order = CANCELLED
    Inventory = RELEASED.

32. Payment timeout là 15 minutes.

33. Payment expiration dùng Backend authoritative timestamp.

34. Late success event không tự reopen Order.

35. Late success event không tự commit released Inventory.

36. Manual Refund chỉ hợp lệ với:
    Order = CANCELLED
    Payment = PAID.

37. Manual Refund không restore Inventory lần hai.

38. Automatic refund không thuộc Architecture.

39. Product Image binary nằm ở Amazon S3.

40. PostgreSQL chỉ lưu Product Image metadata/reference.

41. Mỗi Product tối đa 10 Product Images.

42. Mỗi Product tối đa một thumbnail.

43. Notification read-state là per ADMIN recipient.

44. Global isRead chung cho mọi ADMIN bị cấm.

45. NEW_ORDER được tạo sau successful checkout initiation.

46. NEW_ORDER không đồng nghĩa Payment đã PAID.

47. PAYMENT_SUCCESS chỉ được tạo sau verified Payment success
    và successful Inventory commit.

48. Dashboard New Orders chỉ tính:
    Order = NEW
    Payment = PAID.

49. Reporting không sở hữu Order, Payment hoặc Inventory authoritative state.

50. Revenue chỉ tính COMPLETED + PAID.

51. Best Selling chỉ dựa trên COMPLETED + PAID.

52. Business timezone = Asia/Ho_Chi_Minh UTC+07:00.

53. Backend authoritative cho Discount time và Payment expiration.

54. Currency = VND.

55. Authoritative monetary values phải là integer VND.

56. PERCENTAGE fractional price dùng HALF_UP nearest 1 VND.

57. Rounded sellingPrice phải được dùng trước khi tính OrderItem.totalPrice.

58. Order.totalAmount = SUM(OrderItem.totalPrice).

59. Payment.amount = Order.totalAmount.

60. Product, Cart, Checkout, Order và Payment phải dùng cùng
    monetary calculation rule.

61. OrderItem giữ historical:
    productNameVi,
    productNameEn,
    basePrice,
    sellingPrice,
    quantity,
    totalPrice.

62. Product rename/price change/discount change/disable/soft-delete
    không được mutate historical OrderItem.

63. Locale vi sử dụng OrderItem.productNameVi.

64. Locale en sử dụng OrderItem.productNameEn.

65. Runtime ADMIN authority dựa trên User.role/User.status trong database.

66. ADMIN_EMAILS chỉ bootstrap initial role.

67. ADMIN_EMAILS không re-promote existing demoted User.

68. Runtime operation không được làm mất last ACTIVE ADMIN.

69. Initial bootstrap validation và last-admin runtime protection
    là hai concern riêng.

70. Browser và Frontend input là untrusted đối với Backend.

71. External payOS Webhook là untrusted cho đến khi verified.

72. Google credential là untrusted cho đến khi Backend verified.

73. payOS protocol knowledge nằm trong Payment integration boundary.

74. S3 protocol knowledge nằm trong Product Image integration boundary.

75. Reporting chỉ read source business data.

76. FAQ, Policy và Contact vẫn là static content.

77. Shipping nằm ngoài scope.

78. Không được thêm Shipping Provider.

79. Không được thêm Shipping Fee.

80. Không được thêm Delivery Tracking.

81. Architecture không yêu cầu Kafka/RabbitMQ.

82. Architecture không yêu cầu Redis.

83. Architecture không yêu cầu Kubernetes.

84. Module không được direct modify repository/table-owned state
    của module khác thông qua internal repository abstraction.

85. Cross-module mutation phải thông qua public application interface
    hoặc Commerce Application Coordination Layer.

86. Cross-module dependency không được tạo circular dependency
    không kiểm soát.
```
