4. IMPLEMENTATION PRINCIPLES
IP-001 – Business Module First
Không sử dụng global project structure:
```text
controller/
service/
repository/
entity/

```
cho toàn bộ Backend.
Mỗi business module có internal layers riêng.
IP-002 – No Foreign Repository Mutation
Ví dụ bị cấm:
```text
PaymentService
→ InventoryRepository.save(...)

```
Đúng:
```text
Payment Result Orchestrator
→ InventoryCommandService.commitSale(...)

```
---
IP-003 – Controllers Do Not Orchestrate Business Transactions
Controller chỉ:
```text
Parse HTTP request
Validate structural input
Resolve authenticated actor
Call application use case
Map response

```
Controller không:
```text
directly mutate Entity
coordinate Inventory + Order + Payment
perform state transition manually

```
---
IP-004 – Backend Authority
Backend authoritative cho:
```text
Authorization
Product purchasability
Discount effectiveness
sellingPrice
Order total
Inventory
Order state
Payment state
Refund eligibility
Business time

```
---
IP-005 – External Integration Isolation
```text
Google
payOS
Amazon S3

```
chỉ xuất hiện thông qua adapter boundary.
IP-006 – PostgreSQL Transaction Where Possible
Các cross-module operation sử dụng cùng PostgreSQL được phép nằm trong cùng local transaction.
External payOS/S3 call không nằm trong ACID transaction.

10. PERSISTENCE STRATEGY
10.1. Primary Key
Implementation Decision ID-002
Main persistence entities use:
```text
Java:
Long

PostgreSQL:
BIGINT

Generation:
PostgreSQL SEQUENCE

```
One application sequence:
```text
app_global_id_seq

```
JPA:
```java
GenerationType.SEQUENCE

```
Rationale:
simple;
efficient indexes;
available before insert;
allows Order display code to use generated ID;
no distributed ID requirement.
10.2. Cross-module JPA References
Cross-module relationship được lưu bằng scalar ID.
Ví dụ:
```text
Payment.orderId : Long
Inventory.productId : Long
Order.userId : Long
OrderItem.productId : Long

```
Không dùng:
```text
@ManyToOne
private Payment payment;

```
giữa module khác nhau.
Within-module relation có thể dùng JPA association.

12.4. `discounts`
Implementation Decision: một Product có tối đa một current Discount configuration row.
Column	PostgreSQL Type	Nullable	Constraint / Purpose
`id`	BIGINT	No	PK
`product_id`	BIGINT	No	FK + UNIQUE

`discount_value`	NUMERIC(19,4)	No	CHECK `> 0`

Type-specific DB/application rules:			
```text
PERCENTAGE:
0 < discount_value < 100

FIXED_PRICE:
discount_value must have zero fractional part
discount_value < Product.basePrice

```
Cross-table `FIXED_PRICE < basePrice` được validate trong application transaction.
Một row/Product loại bỏ khả năng overlap ambiguity mà không thêm promotion engine.

18.2. Pricing Algorithm
```text
calculateSellingPrice(product, discount, now):

    basePrice = product.basePrice

    if discount == null:
        return basePrice

    if discount.isActive == false:
        return basePrice

    if now < discount.startAt:
        return basePrice

    if now > discount.endAt:
        return basePrice

    if discount.type == FIXED_PRICE:
        fixed = discount.discountValue.longValueExact()

        assert fixed > 0
        assert fixed < basePrice

        return fixed

    if discount.type == PERCENTAGE:
        percentage = discount.discountValue

        rawDiscount =
            BigDecimal(basePrice)
            * percentage
            / 100

        rawSellingPrice =
            BigDecimal(basePrice)
            - rawDiscount

        sellingPrice =
            rawSellingPrice.setScale(
                0,
                RoundingMode.HALF_UP
            ).longValueExact()

        assert sellingPrice > 0

        return sellingPrice

```
`divide(100)` không thực hiện rounding trung gian.

20. IDENTITY IMPLEMENTATION
20.1. Google Login + CSRF Flow
Browser authentication flow:
```text
App initialization
↓
GET /api/v1/auth/csrf
with credentials: "include"
↓
receive anonymous/current CSRF token in response body
↓
store CSRF token in frontend memory
↓
Google Identity Services
↓
credential
↓
POST /api/v1/auth/google
with:
credentials: "include"
X-XSRF-TOKEN: <csrf-token>
↓
GoogleIdentityVerifierAdapter
↓
verify
↓
extract authoritative claims
↓
find User by googleId
↓
if existing User.status = BLOCKED
→ reject USER_BLOCKED
→ do not establish Authentication
→ do not invoke authentication-success CSRF rotation
→ do not issue JWT
→ do not set BT_ACCESS
↓
create if absent
↓
ADMIN_EMAILS bootstrap only if new
↓
require resulting User.status = ACTIVE
↓
successful Google authentication
↓
establish authenticated Authentication
in the current Spring Security SecurityContext
↓
explicitly invoke configured CsrfAuthenticationStrategy
or Spring Security equivalent authentication-success CSRF cleanup
↓
invalidate/remove old pre-login CSRF token
from the configured CookieCsrfTokenRepository
↓
issue JWT
↓
set HttpOnly BT_ACCESS cookie
↓
GET /api/v1/auth/csrf again
with credentials: "include"
↓
receive fresh authenticated CSRF token
↓
replace cached CSRF token in memory
↓
GET /api/v1/me
↓
normal authenticated state
```
`POST /api/v1/auth/google` is public for authentication but is not CSRF-exempt. A valid CSRF token is required because login is a state-changing browser request.
Because Google Login is a custom controller-driven flow (`AuthController → GoogleAuthenticationService`) rather than a framework-managed form-login authentication flow, implementation must not rely on an implicit Spring Security authentication-success hook. The successful custom login path must explicitly establish the authenticated `Authentication` and invoke the configured `CsrfAuthenticationStrategy`, or an equivalent Spring Security authentication-success CSRF strategy, using the same configured `CookieCsrfTokenRepository`.
Logical behavior is equivalent to:
```java
Authentication authentication =
    createAuthenticatedPrincipal(activeUser);

SecurityContext context =
    SecurityContextHolder.createEmptyContext();

context.setAuthentication(authentication);
SecurityContextHolder.setContext(context);

csrfAuthenticationStrategy.onAuthentication(
    authentication,
    request,
    response
);

// old pre-login CSRF token is invalidated

String jwt =
    jwtTokenService.createToken(activeUser);

writeBtAccessCookie(
    response,
    jwt
);
```
This establishes authentication for the successful login request only; subsequent requests remain authenticated through the `BT_ACCESS` JWT cookie and `JwtAuthenticationFilter`. This requirement does not introduce a server-side login session.
The authentication-success CSRF strategy is invoked only after Google credential verification succeeds and the resulting User is confirmed `ACTIVE`. Invalid Google credentials, validation failures, and `BLOCKED` User login attempts must not establish Authentication, must not invoke authentication-success CSRF rotation, must not issue JWT, and must not set `BT_ACCESS`.
After successful authentication, the old pre-login CSRF token is invalidated before the successful login response completes. The Frontend must call `GET /api/v1/auth/csrf` again and use the returned fresh authenticated CSRF token for later state-changing requests.

```text
BT_ACCESS:
HttpOnly
Secure
SameSite=Lax
```
requires:
```text
Frontend and Backend production deployment
must remain same-site.
```
Valid production shape:
```text

```
because both are HTTPS origins under the same registrable site:

Exact production domain names remain a Deployment Design decision, but `same-site` is a deployment constraint of the selected `SameSite=Lax` authentication strategy, not merely a recommendation.
If a future deployment places Frontend and Backend on unrelated sites, Cookie/CORS/CSRF strategy must be reviewed before production. The current Implementation Specification does not authorize such a deployment without that review.
24.3. CSRF Token Delivery and Mutation Contract
Cookie-based authentication makes the browser send credentials automatically. State-changing browser requests therefore require Spring Security CSRF protection.
Repository:
```text
Spring Security CookieCsrfTokenRepository
```
CSRF repository cookie:
```text
XSRF-TOKEN
HttpOnly = true
Secure = true in prod
SameSite = Lax
```
Because the token is delivered explicitly by `/api/v1/auth/csrf`, frontend JavaScript does not need direct access to this cookie.
Frontend does not depend on reading the API-host `XSRF-TOKEN` cookie directly.
24.3.1. CSRF Endpoint
Endpoint:
```text
GET /api/v1/auth/csrf
```
Actor:
```text
GUEST
USER
ADMIN
```
Backend behavior:
```text
resolve/generate current CsrfToken
↓
return token explicitly in response body
```
Response:
```json
{
  "success": true,
  "data": {
    "token": "<csrf-token>"
  },
  "message": null,
  "timestamp": "2026-08-12T10:30:00+07:00",
  "correlationId": "f58e1f1b-..."
}
```
Frontend storage:
```text
memory only
```
Frontend must not persist CSRF token in:
```text
localStorage
sessionStorage
```
24.3.2. CSRF Mutation Header
Frontend sends:
```text
X-XSRF-TOKEN: <csrf-token>
```
for:
```text
POST
PUT
PATCH
DELETE
```
except endpoints intentionally CSRF-exempt, currently:
```text
POST /api/v1/payments/webhook/payos
```
24.3.3. Login Token Rotation
Flow:
```text
App initialization
↓
GET /api/v1/auth/csrf
↓
receive anonymous/current token
↓
POST /api/v1/auth/google
with X-XSRF-TOKEN
↓
Google credential verified
↓
resulting User confirmed ACTIVE
↓
establish authenticated Authentication
in current SecurityContext
↓
explicitly invoke configured CsrfAuthenticationStrategy
or equivalent Spring Security authentication-success CSRF cleanup
↓
old pre-login CSRF token removed/invalidated
from CookieCsrfTokenRepository
↓
issue JWT
↓
BT_ACCESS set
↓
GET /api/v1/auth/csrf again
↓
receive fresh authenticated token
↓
replace in-memory token
```
The custom `/api/v1/auth/google` path must invoke the configured authentication-success CSRF strategy explicitly. It must not depend on an implicit form-login success handler that is not part of this custom controller flow.
`SecurityConfig` owns/configures the shared `CookieCsrfTokenRepository` and the `CsrfAuthenticationStrategy` or equivalent Spring Security authentication-success strategy. The custom Google Login success path invokes that configured strategy only after successful authentication and ACTIVE-status validation.
Failure behavior:
```text
invalid Google credential
OR resulting User = BLOCKED
OR authentication otherwise fails
↓
do not establish authenticated Authentication
do not invoke authentication-success CSRF rotation
do not issue/set BT_ACCESS
```
A successful Google Login invalidates the pre-login CSRF token before `BT_ACCESS` login completion. The next `GET /api/v1/auth/csrf` returns the fresh authenticated token used by subsequent mutations.
24.3.4. Spring Security Logout Implementation
Logout endpoint:
```text
POST /api/v1/auth/logout
```
Ownership:
```text
Spring Security LogoutFilter
configured through SecurityFilterChain logout DSL
```
`AuthController` does not implement logout business logic. No `LogoutController`, `LogoutService` or `LogoutStatus` is introduced.
Logical `SecurityConfig` design is equivalent to:
```java
http
    .addFilterBefore(jwtAuthenticationFilter, LogoutFilter.class)
    .logout(logout -> logout
        .logoutRequestMatcher(authenticatedPostLogoutMatcher)
        .addLogoutHandler(authenticationCookieCleanupHandler)
        .logoutSuccessHandler(jsonLogoutSuccessHandler)
    );
```
`authenticatedPostLogoutMatcher` is a logical matcher configured inside `SecurityConfig` for `POST /api/v1/auth/logout` that matches only when the current Spring Security context contains a valid authenticated principal. It does not require a new class file.
`JwtAuthenticationFilter` must execute before `LogoutFilter` so Cookie JWT authentication is established before the authenticated logout matcher is evaluated. CSRF validation remains earlier in the filter chain for the state-changing POST request.
If authentication is missing/invalid, the logout matcher does not claim the request; it continues to the normal authenticated-route authorization path and returns the project's standard `401` response. This preserves the current route policy while still using Spring Security's built-in `LogoutFilter` pipeline.
Required logout behavior:
```text
1. Browser sends POST /api/v1/auth/logout
   with credentials: include
   and X-XSRF-TOKEN.

2. Request passes Spring Security CSRF validation.

3. Spring Security LogoutFilter handles the logout request.

4. SecurityContextLogoutHandler clears Authentication,
   SecurityContextHolder and configured SecurityContextRepository state.

5. Authentication-cookie cleanup expires/deletes BT_ACCESS.

6. CsrfLogoutHandler clears the CSRF repository state/token.

7. LogoutSuccessHandler returns the standard JSON API envelope
   with HTTP 200 OK.

8. Frontend clears CurrentUser auth state,
   in-memory CSRF token and authenticated TanStack Query cache.

9. Frontend obtains a new anonymous/current CSRF token through
   GET /api/v1/auth/csrf when a later anonymous mutation/login flow needs it.
```
Spring Security CSRF support must retain its logout cleanup behavior; implementation must not replace the built-in CSRF logout handling with a cookie-only authentication cleanup.
`BT_ACCESS` deletion semantics:
```text
Name = BT_ACCESS
Path = /
HttpOnly = true
Secure = true in production
SameSite = Lax
Domain = same effective AUTH_COOKIE_DOMAIN used at creation, when configured
Max-Age = 0 / expired cookie semantics
```
Cookie creation and cookie deletion must use matching effective `Path` and `Domain` semantics. A deployment with configured `AUTH_COOKIE_DOMAIN` must delete with that same effective Domain; otherwise a stale authentication cookie can remain in the browser.
The authentication-cookie cleanup may be implemented as a `LogoutHandler` configured in `SecurityConfig` and may reuse the existing cookie-writing logic. No additional service abstraction is required solely for logout.
`CsrfLogoutHandler` or equivalent Spring Security logout behavior clears the `CookieCsrfTokenRepository` state. Deleting only `BT_ACCESS` is incomplete and forbidden.
Logout success contract:
```json
{
  "success": true,
  "data": null,
  "message": null,
  "timestamp": "2026-08-12T13:05:00+07:00",
  "correlationId": "f58e1f1b-..."
}
```
HTTP status:
```text
200 OK
```
No redirect, HTML logout page or `204` contract is used by the API.
Repeated logout behavior follows the current authenticated-only route policy:
```text
first authenticated logout + valid CSRF
→ 200 OK
→ authentication/CSRF state cleared

subsequent logout without valid authentication
→ normal 401 security response
```
No new business error code is introduced.

29.2. Effective Price Query
Public list price filter/sort dùng cùng logical formula với `PricingService`.
Pseudo-SQL:
```sql
CASE
    WHEN discount is not effective
        THEN p.base_price

    WHEN discount_type = 'FIXED_PRICE'
        THEN CAST(discount_value AS BIGINT)

    WHEN discount_type = 'PERCENTAGE'
        THEN CAST(
            FLOOR(
                (
                    p.base_price::numeric
                    -
                    (
                        p.base_price::numeric
                        * discount_value
                        / 100
                    )
                )
                + 0.5
            )
            AS BIGINT
        )
END

```
Tất cả authoritative prices positive nên:
```text
FLOOR(raw + 0.5)

```
tương ứng HALF_UP nearest 1 VND.
Repository integration tests phải assert SQL price bằng `PricingService` cho boundary cases `.49`, `.50`, `.51`.
29.3. Admin Product List Soft-delete Behavior
Version 1.0 admin Product list mặc định dùng:
```text

```

29.4. Product Base Price Update vs Existing Discount
Nếu ADMIN update `Product.basePrice`, Backend phải revalidate current Discount configuration trước commit:
```text
basePrice > 0 integer VND

FIXED_PRICE:
0 < discountValue < newBasePrice

PERCENTAGE:
0 < discountValue < 100
AND rounded sellingPrice > 0
```
Nếu existing Discount không còn hợp lệ với new `basePrice`, Product update bị reject; Backend không silently mutate hoặc disable Discount để làm request hợp lệ.

32.1. Upload Consistency
Flow:
```text
1. validate request type/MIME/magic bytes/size
2. validate Product existence as preliminary check
3. upload object to S3 OUTSIDE PostgreSQL transaction
4. begin DB transaction
5. lock Product row PESSIMISTIC_WRITE
6. revalidate Product not soft-deleted
7. recount current images under lock
8. require current count < 10
9. persist ProductImage metadata
10. commit DB transaction
```
Correctness của maximum 10 images nằm ở locked recount + metadata insert. Concurrent upload có thể tạo object tạm trên S3, nhưng chỉ metadata transaction hợp lệ được commit.
Nếu DB persistence/revalidation fail sau S3 success:
```text
attempt S3 delete immediately
retry max 3 times
```
Nếu compensation vẫn fail:
```text
ERROR log
objectKey recorded in log
manual orphan cleanup
```
Orphan object không được expose vì DB metadata không tồn tại.
32.2. Delete Consistency
Flow:
```text
1. DB transaction:
   lock Product
   load target ProductImage
   if target is current thumbnail:
       choose remaining image with smallest sortOrder, then smallest id
       set that image as thumbnail
       if no image remains, Product has no thumbnail
   delete ProductImage metadata
   commit

2. after commit:
   S3 DeleteObject
   retry max 3

```
Nếu S3 delete fail:
```text
metadata remains deleted
object becomes orphan
structured ERROR log
manual cleanup

```
Không rollback metadata thành broken visible reference.
32.3. Thumbnail Concurrency

```text
↓

↓
set all product images isThumbnail=false
↓
```

36. INVENTORY RESERVE ALGORITHM
Within protected transaction:
```text
lock inventories sorted by productId

for each item:

    beforeQuantity =
        inventory.quantity

    beforeReserved =
        inventory.reservedQuantity

    available =
        beforeQuantity - beforeReserved

    if available < requested:
        throw INVENTORY_INSUFFICIENT

    afterQuantity =
        beforeQuantity

    afterReserved =
        beforeReserved + requested

    validate:
        afterReserved <= afterQuantity

    inventory.reservedQuantity =
        afterReserved

    create InventoryTransaction:
        type = RESERVE
        quantityDelta = 0
        reservedQuantityDelta = +requested
        beforeQuantity
        afterQuantity
        beforeReservedQuantity
        afterReservedQuantity
        referenceType = ORDER
        referenceId = orderId
        businessKey =
          RESERVE:ORDER:{orderId}:PRODUCT:{productId}

```

```text
businessKey =
```

49. PAYMENT EXPIRATION AND VERIFIED SUCCESS-TIME ARBITRATION
Scheduler and webhook may race around the 15-minute deadline.
Correctness is based on:
```text
current Payment.status
+
Payment.expiresAt
+
verified effective payment-success time
+
Order/Payment/Inventory locks
```
DB locks serialize competing mutations; they do not define business time.
49.1. Effective Payment Success Time
After payOS signature verification succeeds, resolve:
```text
effectivePaymentSuccessTime
```
Priority:
```text
1. verified provider transaction timestamp
   only if:
   - field is present in signed provider data
   - adapter contract test confirms parse format
   - adapter contract test confirms timezone semantics

2. conservative webhook-receipt fallback
   only as defined below
```
Current payOS docs include signed `transactionDateTime`, but its payment-webhook timezone semantics are not explicitly documented. Until contract verification proves the timezone mapping, implementation must not guess.
Fallback policy when provider transaction time cannot be interpreted reliably:
```text
if verified webhookReceivedAt <= Payment.expiresAt:
    effectivePaymentSuccessTime = webhookReceivedAt
    // conservative upper bound; receipt occurred before/on expiry

else:
    success time cannot be proven to be before expiry
    do not run normal CG-002
    expire still-PENDING Payment
    set manualResolutionRequired = true
    manualResolutionNote =
      PAYMENT_SUCCESS_TIME_UNVERIFIABLE_AFTER_EXPIRY
```
This fallback does not trust frontend, returnUrl or unsigned timestamps.
49.2. Verified Success Arbitration
After verified provider event validation:
```text
lock Order
↓
lock Payment
↓
re-read Payment.status
```
Case A — Payment already `PAID`:
```text
idempotent success
```
Case B — Payment already terminal:
```text
FAILED
CANCELLED
EXPIRED
```
Result:
```text
do not set PAID
do not reopen Order
do not SALE Inventory
manualResolutionRequired = true
audit/log late payment
```
This preserves the frozen late-success rule.
Case C — Payment still `PENDING`:
resolve `effectivePaymentSuccessTime`.
If:
```text
effectivePaymentSuccessTime <= Payment.expiresAt
```
run normal `CG-002`:
```text
Inventory SALE exactly once
Payment → PAID
Payment.paidAt = effectivePaymentSuccessTime
Order remains NEW
PAYMENT_SUCCESS
```
This remains valid even if webhook delivery reaches Backend after `expiresAt`, as long as Payment is still `PENDING` and verified provider time proves the transaction happened before/on expiry.
If:
```text
effectivePaymentSuccessTime > Payment.expiresAt
```
do not run normal `CG-002`. Converge:
```text
Payment → EXPIRED
Order → CANCELLED
Inventory → RELEASED exactly once
InventoryTransaction.RELEASE
PAYMENT_FAILED actualStatus=EXPIRED
manualResolutionRequired = true
manualResolutionNote = LATE_VERIFIED_PAYMENT_SUCCESS
```
Do not:
```text
set Payment PAID
reopen Order
SALE Inventory
```
49.3. Required Success Pseudo-code
```text
processVerifiedSuccess(event):

    validate verified provider event

    order = lock Order
    payment = lock Payment

    if payment.status == PAID:
        return idempotent success

    if payment.status in
       FAILED, CANCELLED, EXPIRED:

        markManualResolutionRequired()
        auditLateSuccess()
        return

    require payment.status == PENDING

    successTime =
        resolveVerifiedPaymentSuccessTime(event)

    if successTime is UNVERIFIABLE_AFTER_EXPIRY:

        expirePendingPayment()
        releaseInventoryExactlyOnce()
        cancelOrder()
        createPaymentFailed(EXPIRED)
        markManualResolutionRequired(
            PAYMENT_SUCCESS_TIME_UNVERIFIABLE_AFTER_EXPIRY
        )
        return

    if successTime > payment.expiresAt:

        expirePendingPayment()
        releaseInventoryExactlyOnce()
        cancelOrder()
        createPaymentFailed(EXPIRED)
        markManualResolutionRequired(
            LATE_VERIFIED_PAYMENT_SUCCESS
        )
        return

    commitInventorySaleExactlyOnce()

    payment.status = PAID
    payment.paidAt = successTime

    Order remains NEW

    create PAYMENT_SUCCESS

    commit
```

63. CG-007 FINALIZATION
Method:
```java
CheckoutFinalizationService.finalizeCheckout()
@Transactional

```
Steps:
```text
1. lock CheckoutOperation

2. if COMPLETED:
       return idempotent success

3. require state = PAYOS_CREATED

4. lock Order, then Payment
   using global business lock order

5. require Order = NEW
   require Payment not in FAILED/CANCELLED/EXPIRED/REFUNDED

   normal canonical case:
       Payment = PENDING
       Inventory reservation remains RESERVED

   verified-success race case:
       Payment = PAID
       allowed only because CG-002 already processed a verified success event;
       CG-007 itself does not change Payment or Inventory

6. load CheckoutOperationItems

7. for each snapshot:
       DELETE CartItem
       WHERE id = snapshot.cartItemId
         AND version = snapshot.cartItemVersion

   if CartItem no longer exists:
       treated as already finalized

   if version changed:
       preserve current CartItem
       because it represents user modification after checkout snapshot

8. create Notification:
       type NEW_ORDER
       dedupKey NEW_ORDER:ORDER:{orderId}

9. create NotificationRecipient rows

10. set CheckoutOperation:
        state = COMPLETED
        completedAt = now

11. commit

```

```text

returns CheckoutResponse

```

```mermaid
    participant N as Notification
    participant DB as PostgreSQL

    J->>Op: Find PAYOS_CREATED
    J->>DB: Begin transaction
    J->>Op: Lock operation
    J->>DB: Lock Order then Payment and validate state

    alt Already COMPLETED
        J-->>J: replay result
    else PAYOS_CREATED
        J->>Pay: verify provider correlation persisted
        J->>Cart: conditional delete checked items
        J->>N: insert NEW_ORDER ON CONFLICT DO NOTHING
        J->>Op: state = COMPLETED
        J->>DB: Commit
    end

```

64.3. CG-007 vs Payment/Order Terminal Race
`Recoverability ≠ Successful Finalization`. Recovery only resumes the same required Phase C effects; it does not authorize early success.
`CheckoutFinalizationService` serializes against payment/terminal flows using:
```text
CheckoutOperation
→ Order
→ Payment
```
Outcomes after locks:
```text
Order = NEW + Payment = PENDING
→ finalize Cart + NEW_ORDER + CheckoutOperation

Order = NEW + Payment = PAID
→ verified success already won the race
→ finalize only Cart + NEW_ORDER + CheckoutOperation
→ do not mutate Payment/Inventory

Order != NEW
OR Payment in FAILED/CANCELLED/EXPIRED/REFUNDED
→ do not clear Cart
→ do not create NEW_ORDER
→ no successful CheckoutResponse
→ structured observable recovery/error state
```
A retry/resume never creates a second Order, OrderItems, Payment, payOS Payment Information, reservation, RESERVE audit or uncontrolled `NEW_ORDER`. It only removes the checked-out CartItems captured in CheckoutOperationItem snapshots.
65. CG-002 PAYMENT SUCCESS
Verified provider data is parsed and validated before the business transaction.
Then:
```java
PaymentResultApplicationService.processSuccess()
@Transactional
```
Steps:
```text
1. determine orderId from verified provider event

2. lock Order

3. lock Payment

4. if Payment = PAID:
       duplicate webhook
       return idempotent success

5. if Payment in FAILED/CANCELLED/EXPIRED:
       mark manualResolutionRequired
       log/audit late event
       return

6. require Payment = PENDING

7. validate:
       amount matches
       provider payment link matches
       Order.status = NEW

8. resolve effectivePaymentSuccessTime
   using Section 49

9. if effectivePaymentSuccessTime cannot be proven
   before/on expiry after expiry has passed:
       expire PENDING Payment
       cancel Order
       RELEASE Inventory exactly once
       PAYMENT_FAILED actualStatus=EXPIRED
       manualResolutionRequired=true
       return

10. if effectivePaymentSuccessTime > Payment.expiresAt:
        expire PENDING Payment
        cancel Order
        RELEASE Inventory exactly once
        PAYMENT_FAILED actualStatus=EXPIRED
        manualResolutionRequired=true
        return

11. lock Inventory rows sorted productId

12. for each OrderItem:
        commit SALE
        create SALE audit
        unique businessKey

13. Payment.status = PAID
    paidAt = effectivePaymentSuccessTime
    externalTransactionIdentifier =
        verified provider reference

14. Order remains NEW

15. persist PAYMENT_SUCCESS
    dedupKey PAYMENT_SUCCESS:PAYMENT:{id}

16. commit
```
Architecture mandates `Order remains NEW` after payment success.

68.2. Scheduler Detection
```mermaid
sequenceDiagram
    participant Job as PaymentExpirationJob
    participant O as Order
    participant P as Payment
    participant I as Inventory
    participant N as Notification

    Job->>P: Query PENDING and expires_at <= now

    loop each Payment ID
        Job->>O: lock Order
        Job->>P: lock Payment
        Job->>P: re-read status + expiresAt
```

69. CG-004 PAID ORDER CANCELLATION
`OrderCancellationApplicationService.cancel(orderId, adminId)`
69.1. Pending Payment ADMIN Cancellation
Local business precondition:
```text
Order = NEW
Payment = PENDING
```
Authoritative local transaction:
```text
BEGIN DB TX

lock Order
lock Payment
lock Inventory rows sorted by Product ID

Order → CANCELLED
Payment → CANCELLED
Inventory → RELEASED exactly once
InventoryTransaction.RELEASE
PAYMENT_FAILED actualStatus=CANCELLED

COMMIT
```
Only after local commit:
```text
best-effort provider payment-request cancellation
through Payment/payOS adapter
```
Current provider mapping:
```text
PayOSClient.cancelPaymentRequest(...)
→ POST /v2/payment-requests/{id}/cancel
```
No payOS network call is executed while holding Order/Payment/Inventory DB locks.
If provider cancellation fails:
```text
do not rollback local cancellation
do not restore Payment PENDING
do not re-reserve Inventory
```
Structured WARN/ERROR contains:
```text
event = PAYOS_PROVIDER_CANCEL_FAILED
orderId
paymentId
providerPaymentLinkId
correlationId
provider cancel result/error
```
The adapter may perform bounded best-effort retry. Operational retry is allowed, but no new business status is introduced.
If provider cancellation fails and a verified payment success later arrives while local state is:
```text
Order = CANCELLED
Payment = CANCELLED
Inventory = RELEASED
```
reuse the frozen late-success rule:
```text
do not reopen Order
do not set normal business flow to PAID
do not SALE Inventory
manualResolutionRequired = true
audit/log late success
```

```text
commit
```

SEC-LOGIN-CSRF-001 – Successful custom Google Login rotates CSRF state
```text
anonymous/pre-login CSRF token A
↓
POST /api/v1/auth/google
with valid token A
↓
Google authentication succeeds
↓
resulting User is ACTIVE
↓
Authentication established
↓
configured CsrfAuthenticationStrategy invoked
↓
old pre-login CSRF token invalidated
↓
BT_ACCESS returned
↓
GET /api/v1/auth/csrf
```
Expected:
```text
login succeeds
old pre-login CSRF repository token is invalidated
fresh authenticated CSRF token B is returned
token B is used for later mutations
```
SEC-LOGIN-CSRF-002 – Old pre-login CSRF cannot be reused after login
```text
successful Google Login using pre-login token A
↓
authentication-success CSRF rotation completes
↓
attempt authenticated state-changing request
using old token A
```
Expected:
```text
request rejected by CSRF validation
old pre-login token is not reusable
frontend must use fresh post-login token B
```
SEC-LOGIN-CSRF-003 – Failed/BLOCKED login does not rotate authentication-success CSRF state
```text
valid pre-login CSRF token A
↓
POST /api/v1/auth/google
↓
invalid Google credential
OR resulting User.status = BLOCKED
```
Expected:
```text
login fails
```

107. IMPLEMENTATION DECISIONS
ID-001 – Technology Baseline
Context: greenfield KLTN Modular Monolith.
Decision: Java 21 + Spring Boot 3.5.16; Next.js 16.2.11 App Router.
Rationale: stable, supported ecosystem, team-friendly.
Trade-off: not using newest Spring Boot major.
Related: ADR-001, ADR-014.
ID-002 – Primary Key
Decision: PostgreSQL sequence-generated BIGINT / Java Long.
Rationale: simple and efficient.
Trade-off: IDs are enumerable; authorization must never depend on obscurity.
Related: ADR-002, ADR-015.
ID-003 – Monetary Type
Decision: BIGINT/long for VND money; NUMERIC/BigDecimal for percentage.
Rationale: no floating-point monetary error.
Related: ADR-010.
ID-004 – Initial ADMIN Validation
Decision: prod `ApplicationRunner` fail-fast when no ACTIVE ADMIN and ADMIN_EMAILS empty/invalid.
Related: Identity architecture.
ID-005 – Last ADMIN Lock
Decision: pessimistically lock all ACTIVE ADMIN rows.
Rationale: simple concurrency correctness.
Related: NFR-REL-006.
ID-006 – JWT Storage
Decision: HttpOnly Secure SameSite=Lax cookie. Authentication-cookie creation and logout deletion use matching effective `Path`/`Domain` semantics.
Rationale: token inaccessible to frontend JS while logout can reliably remove the same browser cookie.
Trade-off: requires CSRF protection and same-site production domain configuration.
ID-007 – JWT Cryptography
Decision: HS256, 2-hour TTL.
Rationale: single Backend runtime; no asymmetric key-distribution requirement.
Trade-off: no refresh token; User re-login after expiration.
ID-008 – S3 Key / Compensation
Decision: `products/{productId}/{uuid}.{ext}`; synchronous cleanup retries.
Related: ADR-005.
ID-009 – Cart Checkout Scope
Decision: checkout entire current Cart snapshot.
Rationale: SRS defines no partial selection.
ID-010 – Inventory Lock
Decision: `PESSIMISTIC_WRITE`, sorted by Product ID.
Rationale: multi-product consistency and simple audit.
Related: ADR-006.
ID-011 – Payment / Order State Lock
Decision: pessimistic Order then Payment lock.
Rationale: resolve webhook/expiration/cancellation races.
ID-012 – payOS Adapter
Decision: Spring `RestClient` adapter behind `PayOSClient`.
Rationale: isolate provider contract.
Related: ADR-004.
ID-013 – Payment Expiration
Decision: Spring `@Scheduled`, 30-second scan, 100 candidates, transaction per Payment.
Related: Payment Expiration Architecture.
ID-014 – Notification Dedup
Decision: unique `notifications.dedup_key`.
Related: ADR-013, ADR-016.
ID-015 – Checkout Idempotency
Decision: `Idempotency-Key` + PostgreSQL `checkout_operations`.
Related: FR-ORDER-010, ADR-011.
ID-016 – CG-007 Recovery
Decision: explicit CheckoutOperation workflow record + recovery job.
Rationale: same mechanism solves retry, response replay and Phase C recovery without broker.
Related: CG-007, ADR-011, ADR-012.
ID-017 – API Versioning
Decision: `/api/v1`.
ID-018 – Database Migration
Decision: Flyway.
Related: NFR-MAINT-002.
ID-019 – Frontend Query / Cache
Decision: Server Components for public read pages, TanStack Query for authenticated/dynamic state.
Related: ADR-014.
ID-020 – Frontend Validation
Decision: Zod.
Rationale: reusable typed UX validation.
ID-021 – Cookie Authentication and CSRF Token Delivery
Context:
Browser uses HttpOnly JWT cookie authentication and therefore needs an explicit CSRF lifecycle and a complete framework-owned logout path.
Decision:
```text
JWT:
HttpOnly
Secure
SameSite=Lax

Frontend and Backend:
same-site production deployment

CSRF:
GET /api/v1/auth/csrf

Frontend:
CSRF token in memory

Mutation:
X-XSRF-TOKEN

Browser fetch:
credentials: include

Google Login authentication success:
successful Google authentication
→ establish authenticated Authentication
→ explicitly invoke configured CsrfAuthenticationStrategy
  or equivalent Spring Security authentication-success CSRF cleanup
→ invalidate old pre-login CSRF token
→ issue/set BT_ACCESS
→ frontend GET /api/v1/auth/csrf again
→ receive/use fresh authenticated CSRF token

Google Login failure/BLOCKED:
no authenticated Authentication
→ no authentication-success CSRF rotation
→ no JWT / BT_ACCESS

Logout:
Spring Security LogoutFilter / logout DSL handles
POST /api/v1/auth/logout

Filter order:
CSRF validation
→ JwtAuthenticationFilter
→ LogoutFilter

Authenticated-only logout matcher:
POST /api/v1/auth/logout
+
valid authenticated principal

Logout clears:
SecurityContext
BT_ACCESS authentication cookie
CSRF repository state

Logout response:
HTTP 200 + standard JSON API envelope
```
Authentication cookie deletion must match the original effective `Path` and `Domain` used for cookie creation. When `AUTH_COOKIE_DOMAIN` is configured, the logout deletion cookie uses that same effective Domain.
Rationale:
Avoid requiring frontend JavaScript to directly read the authentication token or the API-host CSRF cookie; ensure the custom controller-driven Google Login explicitly receives authentication-success CSRF cleanup instead of relying on an unrelated implicit form-login hook; and avoid a custom partial logout implementation that clears `BT_ACCESS` but leaves Spring Security/CSRF state inconsistent.
Trade-off:
Deployment must preserve same-site cookie semantics. Logout configuration must preserve Spring Security's CSRF/logout handlers while providing the project-standard JSON success response. An unrelated-site deployment requires security-strategy review before production.
Related:
```text
NFR-SEC-*
Identity Architecture
Security Architecture
```

ID-022 – Product Image S3 Transaction Boundary
Context:
S3 is external to PostgreSQL and Product Image metadata must still respect the maximum-image and ownership rules.
Decision:
```text

Metadata finalization uses a short Product-locked

compensate with S3 DeleteObject.
```
Rationale:

ID-023 – Payment Expiration and Verified Success-Time Arbitration
Context:
Expiration scheduler and payment-success webhook can race around the frozen 15-minute deadline.
Decision:
```text
Payment.expiresAt is business authority.

Scheduler execution time does not extend Payment window.

Verified provider transaction time determines whether
a valid payment occurred before expiration where
the provider contract reliably supports this.

If provider transaction time cannot be safely interpreted,
the conservative fallback in Section 49 applies;
the implementation does not silently guess timezone semantics.
```
Rationale:
Avoid accepting a payment as on-time merely because the expiration scheduler had not processed the row yet.
Trade-off:
Provider timestamp parsing and timezone semantics must be contract-tested and re-verified against current official payOS documentation.
Related:
```text
FR-PAY-*
BR-TIME-001
CG-002
CG-003
Payment Expiration Architecture
```

ID-024 – Pending Admin Cancellation and payOS Provider Cancellation
Context:
A local ADMIN cancellation of a PENDING Payment can leave an active provider payment request unless the provider is also asked to cancel it.
Decision:
```text
Local PostgreSQL cancellation is authoritative.

Provider payment-request cancellation is best-effort
after local commit.

Provider cancellation failure does not rollback
Order/Payment/Inventory local outcome.
```
Rationale:
Never hold business DB locks across payOS network I/O and never make frozen local cancellation correctness depend on provider availability.
Trade-off:
Provider cancellation can fail after local commit; late verified payment is handled by the existing manual-resolution late-success rule.
Related:
```text
CG-004
Payment Architecture
payOS Adapter
```

Decision:

```text
Default maximum upload size:
5 MiB per image

Configuration:
IMAGE_MAX_BYTES
```
Rationale:
Protect network, memory and storage while supporting normal Product gallery images.
Trade-off:
This is a configurable implementation limit, not new SRS business scope.
